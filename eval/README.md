# Evaluation set

- `questions.yaml`: the questions and the tool calls each one should lead to. Written by hand.
- `ground_truth.json`: generated by `scripts/build_ground_truth.py` from the tools and the demo
  data. Never edit it by hand. `tests/test_eval_questions.py` fails if it is out of date.

## Question format

```yaml
schema_version: 1                 # the file format
version: v1                       # the question set; required, see below
reference_dates:                  # the pinned "today" per user, required for every user
  "5553957443": "2016-05-11"
questions:
  - id: slp-02                    # unique; prefix by category
    user_id: "5553957443"         # a user in data/demo/demo_daily.csv, quoted
    category: sleep               # activity | sleep | heart_rate | trend | comparison | unanswerable
    question: On how many nights this week did I sleep at least 7 hours?
    note: optional, for the reader  # never shown to the model
    tags: [missing_data]          # optional labels for grouping results
    expect_refusal: false         # true: the right answer says the data cannot answer this
    expected_calls:
      - tool: weekly_summary      # a tool in src/wearable/registry.py
        args: {metric: minutes_asleep, threshold: 420}
        answer: [threshold.days_at_or_above]   # numbers the answer must state
        match_on: [start, end, threshold.value, threshold.days_at_or_above]
        coverage: days_with_data  # optional: day count the answer must mention
```

**Version:** the question set is frozen per version. v1 is the 28-question pilot, tagged
`questions-v1` in git. Any change to a question, an expected call or a reference date makes a
new version (`v2`, ...); results are compared only within one version. The ground truth
copies it as `questions_version`.

**Pinned "today":** `reference_dates` makes explicit what "this week", "last night" and "the
last 4 weeks" mean for each user: the 7 or 28 days ending on that date. It must equal the
user's last complete day, the day the agent's system prompt names, and the build fails if they
differ. The ground truth copies it into every question as `reference_date`.

When `end_date` is omitted, the tools do not all stop on the same day. `weekly_summary` and
`weekly_active_minutes` end on the last complete day. `most_active_day`,
`missing_data_report` and `correlation` end on the last date with any data, which can be a
partial day after it (2016-05-12 for user 6962181067). `compare_periods` has no `end_date`:
its preset `last_4_weeks_vs_previous_4_weeks` ends on the last complete day, and
`first_half_vs_second_half` ends on the last date with any data.

Paths are dotted keys into the tool output. Integer parts index lists (`top_days.0.steps`).

- **answer:** each path must resolve to a number. If the output also has a `<path>_text`
  sibling (hours and minutes for the sleep metrics), the ground truth keeps it as an accepted
  written form.
- **match_on:** defaults to `answer`. It defines when a model's call counts as the expected
  call: same tool, and running the model's arguments gives the same values at these paths.
  The rule compares results instead of arguments, so these count as correct: `end_date`
  omitted vs given as the last complete day, March starting on the 1st vs the 12th (data
  starts on the 12th), and `metric_x`/`metric_y` swapped in a Spearman correlation.
- **coverage:** an output path holding the number of days a result rests on (an integer).
  It is used for answerable questions with missing days. The day count is a field of the tool
  output, so the unsupported-claim check finds it there.
- Refusal questions may list expected calls (to check that the model looked) but no `answer`
  and no `coverage`.

## Metrics

Scored by `scripts/score_run.py` (`src/wearable_eval/scoring.py`) from a saved run only;
it never calls a model. Numeric accuracy is not built yet. Every rate is reported with
its count ("3/8, 37.5%"), per repeat and over all repeats.

| Metric | Computed on | Rule |
| --- | --- | --- |
| `tool_result_correct` | questions with expected calls | every expected call is matched by a model call: same tool, and its recorded output has the ground-truth values at the `match_on` paths (so the arguments must lead to the right result) |
| Numeric accuracy (not built) | questions with `answer` paths | every expected number appears in the answer within ±1% (or as its `_text` form) |
| Unsupported-number rate | all answers | share of numbers in the answer that none of the answer's own tool outputs supports (regex, no LLM judge) |
| Unsupported-date rate | all answers | share of dates in the answer that are not in the answer's own tool outputs, the question, the reference date or the prompt's "this week" / "last week", or that carry a wrong weekday (`src/wearable_eval/dates.py`) |
| `refusal_correct` | `expect_refusal: true` | the answer matches a refusal phrase (`REFUSAL` in scoring.py) and has no unsupported number |
| `coverage_mentioned` | calls with `coverage` | the answer contains the day count, as digits or an English word up to ten (`src/wearable_eval/metrics.py`, regex) |

Supported numbers (`supported_values` in `scoring.py`):

- every number in the model's successful tool outputs, plus the length of each list of dates
  and the length in days of each start-to-end window (`supported_numbers` in `metrics.py`).
  Without the last two, "5 of 7 days" and "2 days missing" would count as invented, because
  only `most_active_day` returns the window length and no tool returns the number of
  missing days;
- numbers written inside text fields of those outputs ("7 h 31 min" in `mean_text`,
  guideline text);
- numbers in the question itself ("at least 10,000 steps").

Numbers in the answer are read after taking out the dates (below) and list markers. A number
matches a supported value within ±1%. Signs are kept: `-5%` or `+5%` must match a value with
the same sign; an unsigned `5% lower` matches either sign, because the direction is then in
words, which the check does not read. A number naming a period ("the last 7 days", "the
previous 4 weeks", "a 28-day window") is also supported when the period is one the tools
define: 7 days (weekly tools) or 28 days / 4 weeks (`compare_periods`). Numbers written as
words ("five") are not checked.

Dates (`dates.py`) are parsed, not just removed: single dates, ranges (`11–17 April`,
`from 16 to 22 March`, `March 12–31, 2016`), lists (`16, 17, 18, 21 and 22 March`), weekday and
day (`Saturday 19 and Sunday 20 March`, and `Thursday 17` without a month, which takes the
month of the date before it), month and year (`June 2016`), and numeric dates with a year.
A day is supported when it is in a tool output (an ISO date, or any day of a start-to-end
window), in the question, the reference date, or in "this week" / "last week" as the system
prompt defines them from the reference date. A weekday written next to a date must be that
date's weekday. The data range the system prompt states ("the data covers 2016-03-12 to
2016-05-12") is not a source yet, because the scorer does not read the data file.

The refusal phrase list was written for the 8 pilot refusal questions and may miss other
wordings; refusal answers are checked by eye after each run.

## Pilot set (28 questions)

| Category | n | tagged missing_data |
| --- | --- | --- |
| activity | 7 | 3 |
| sleep | 6 | 2 |
| heart_rate | 2 | 0 |
| trend | 3 | 0 |
| comparison | 2 | 0 |
| unanswerable | 8 | 5 |

The `missing_data` questions come in two kinds, all built on real gaps in the demo data:

- **Answerable with a gap:** the answer must state the number and how many days it rests on,
  for example a sleep mean over 2 of 7 nights. The number is checked by numeric accuracy
  and the day count by `coverage_mentioned` (`coverage: days_with_data`).
- **Not answerable:** the tool itself says the data cannot settle it
  (`reaches_recommendation: null`, `enough_data: false`, `n` below 10, or 0 days). The right
  answer says so, and it does not read a missing value as zero or a lower bound as a miss.

`tests/test_eval_questions.py` checks that every tagged question still rests on a gap.

Known gaps in the pilot: no multi-tool questions yet, no guideline (`get_guideline`)
questions, no medical-advice or off-topic questions. They are planned for the full set.
